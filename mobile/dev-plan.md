# 开发计划

> 执行状态只看 [TASKS.md](TASKS.md)。手机行为只看 [SPEC.md](SPEC.md)。桌面 WebDAV 行为只看仓库根目录的 [SPEC.md](../SPEC.md)。本文件是阅读顺序，不是第二份规格。

## 顺序

1. **T1 冻结手机端文档。** `mobile/SPEC.md`、`mobile/ARCH.md`、`mobile/prd.md`、本文件、`mobile/TASKS.md`、`mobile/todo.md`、历史存储的 schema。规则句子只放在 SPEC。
2. **T2 看见红灯。** 在现有 `build/copyq-tests` 里加手机契约用例。用例失败的原因是守卫和主题读取还没实现，不是编译失败，也不是没连上手机。记录进 SPEC 第 5 节。
3. **T3 共享核心变绿。** 历史存储、主题颜色读取、残缺上传确认，都在电脑上的测试进程里变绿。这一步仍不产生 APK 或 IPA。
4. **T4 Android 首次界面。** 历史、标签页、查找、编辑、标志和主题。分享入口按 M9。没有备份页之前，不把这一步标成首次完成。
5. **T5 Android 备份页。** 接到已经存在的配置打包和 WebDAV 客户端，不重写 zip。
6. **T6 iOS 同一套界面和同一套规则。** 包括系统分享入口。只做完 Android 时，M20 仍是未完成。
7. **T7 真机核对。** 模拟器通过不能拿来签 M8 和 M9。剪贴板是否允许读取，只有真机说了算。

T2 依赖 T1。T3 依赖 T2 的红灯记录。T4 依赖 T3。T5 依赖 T4 的界面壳，也依赖桌面同步代码保持现有测试通过。T6 依赖 T5 的同一套界面，不另起一份 iOS 专用规则。T7 依赖 T6。

## 这一步实际做了什么

只做了 T1。没有测试，没有 Android 工程，没有 iOS 工程，没有把 `upstream/android` 合并进来。

桌面 WebDAV 那一次是先有代码、后补规格。这一次按相反的顺序：先写句子，再允许 T2 去造红灯。不要把 T1 说成移植已经开始写代码。

## 实现时不准改的方向

技术约束在 [ARCH.md](ARCH.md)。这里只保留会让计划跑偏的几条：

- 两端共用一套界面描述。不要先写完 Kotlin 界面，再让 SwiftUI 照着抄。
- zip、清单、错误码继续用桌面已经测过的那套。手机只加「上传前的那句警告」。
- 不新建依赖去解析主题或打包。
- 不把空的 Qt 工程提交上来冒充 T4。

## 验收命令

T1 没有测试命令。桌面这条命令仍然只证明桌面同步，不能证明手机：

```
source utils/env.sh
export QT_QPA_PLATFORM=offscreen
build/copyq-tests testConfigSync
```

T2 之后才会有手机用例的过滤名。在 SPEC 第 5 节记下真实名字之前，不要发明一条绿色命令。

`gate_check.sh` 还不能当作手机端的验收。它不认识还没写出来的用例，而且仓库里已有与这次无关的告警。
